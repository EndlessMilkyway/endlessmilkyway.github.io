#### 역할

- **요구사항·설계**
  - 고객사와 프로토타입 화면으로 화면 구성 합의
  - 앞선 프로젝트의 3계층 구조, 공통 다이얼로그, 표시 컨트롤, DI 골격을 가져와 이 라인에 맞게 수정
- **Core 개발**
  - 마스터 프로그램 접속 TCP 클라이언트 (자동 재연결)
  - STX/ETX 프레이밍과 공정 상태 전문 파싱
  - 시프트·오류 판단 상태 기계, 알람 상태 기계
  - USB 타워 램프 연동 (제조사 네이티브 라이브러리 호출)
  - 오류 이력 영속화, 설정 검증
- **Presentation 개발**
  - 공정 배치도 셀과 공정 상태 표를 사용자 컨트롤로 만들어 재사용 (배치도 14곳, 표 2곳)
  - 설정 화면의 저장·취소 처리
- **테스트·배포**
  - xUnit 테스트 102개 (TCP 루프백 통합 테스트 포함)
  - 버전 태그 푸시로 GitHub Actions 릴리스
  - 현장 시운전

#### 주요 기능

- 14개 공정의 커밋번호·바디번호·장착 오류 실시간 표시 (배치도 + 공정 상태 표)
- 마스터 프로그램 자동 재연결
- 깨진 전문 전체 거부, 다음 시작 문자로 재동기화
- 오류 알람 (화면 알람, 타워 램프 점등·멜로디)
- 작업자 음소거 (램프는 켜 둔 채 소리만 끔)

- 작업 이력·오류 로그

- 시뮬레이션 모드 (기록 파일을 실제 수신과 같은 경로로 재생)

##### 문제 배경

수신 파이프라인 통합 테스트가 가끔 실패했습니다. 타이밍 문제로 넘기기 쉬운 증상이었지만, 24시간 운영되는 현장에서 같은 경쟁 상태가 생기면 원인을 찾기가 훨씬 어렵다고 판단했습니다. 같은 테스트를 반복 실행해 실패율을 재 보니 40회 중 7회였습니다.

##### 개선 방법

원인은 통신 정지 경로에 있었습니다. 정지 요청과 상대편의 연결 리셋이 겹치면 예외가 정지 메서드를 부른 쪽, 즉 앱 종료 경로까지 올라갔습니다. 이 경우 종료 시 타워 램프 소등 같은 이후 정리 단계가 생략될 수 있었습니다. 정지 요청 이후에 발생한 예외는 정상 종료로 처리하도록 고쳤습니다.

이어서 같은 종류의 구멍이 또 있는지 연결 루프 전체를 점검했습니다.

- 연결·끊김·연결 실패 이벤트를 받는 쪽 코드가 예외를 던지면 재연결 루프 자체가 멈추는 경로가 있었습니다. 24시간 운영에서 재연결 루프가 멈추면, 마스터가 복구돼도 현황판은 다시 붙지 않습니다.
- 모든 이벤트 발행을 격리 함수로 감싸, 구독자 예외는 진단 이벤트와 로그로만 남기고 루프는 계속 돌게 했습니다.
- 구독자가 예외를 던져도 루프가 유지되는지 검증하는 루프백 테스트 3개를 추가했습니다.

마지막으로 "재연결 루프는 어떤 예외로도 멈추면 안 되고, 새 이벤트도 같은 격리 방식으로 발행한다", "간헐적 테스트 실패는 타이밍 문제로 넘기지 말고 실제 경쟁 상태를 의심한다"는 규칙을 프로젝트 문서에 남겼습니다.

##### 결과

같은 조건으로 반복 실행해 실패가 더 이상 재현되지 않음을 확인했습니다. 앱 종료 시 정리 단계가 빠지는 경로와 재연결 루프가 멈추는 경로를 함께 막았습니다.

##### 문제 배경

마스터는 매번 14개 공정 전체 상태를 스냅샷으로 보내므로, 오류가 난 차체는 여러 스냅샷에 연속해서 나타나고 공정을 따라 자리도 옮깁니다. 받은 스냅샷을 그대로 알람으로 쓰면 같은 오류를 계속 다시 알리게 됩니다. 연결이 끊겼다 다시 붙거나 프로그램을 재시작한 직후에도, 그 사이의 이동을 작업 이력으로 잘못 남기거나 이미 알린 오류를 다시 알릴 수 있었습니다.

처음에는 이 판단이 화면 ViewModel 안에 상태 필드로 흩어져 있었습니다. 테스트 프로젝트는 Core만 참조하므로, 이 규칙들을 단위 테스트로 검증할 수 없었습니다.

##### 개선 방법

판단 로직을 Core의 상태 기계로 분리하고, ViewModel은 판단 결과에 따라 로그·오류 메시지·알람 통지만 하도록 바꿨습니다. 규칙은 다음과 같이 정했습니다.

- **작업 이력은 공정(자리) 기준:** 그 자리에 직전과 다른 차체가 들어오면 기록합니다. 빈 자리도 기록해, 차체가 빠졌다가 같은 차체가 다시 들어오는 경우도 놓치지 않게 했습니다.
- **오류 알림은 차체 기준:** 그 차체의 오류 종류가 마지막으로 본 것과 달라질 때만 알립니다. 오류 차체가 다음 공정으로 옮겨도 다시 알리지 않고, 오류를 달고 새로 들어온 차체와 HEV 오류가 HEV·V2Lc 동시 오류로 커진 경우는 알립니다. 라인을 떠난 차체는 기준에서 자연히 빠집니다.
- **재동기화:** 첫 스냅샷과 연결이 끊긴 뒤의 첫 스냅샷은 관측하지 못한 이동이 섞여 있으므로 작업 이력은 남기지 않고, 이미 걸려 있는 오류는 알립니다.
- **기준선 영속화:** 차체별 마지막 오류 종류를 상태 파일에 저장하고 시작할 때 복원해, 재시작 직후 여전히 오류 중인 차체를 다시 알리지 않게 했습니다. 저장 이벤트는 기준선 갱신이 끝난 뒤에 발행하도록 순서를 고정했습니다.

##### 결과

알림·작업 이력 규칙을 단위 테스트 15개로 고정했고, 화면 코드는 판단 결과를 반영하는 역할만 남았습니다.

</Case>
