- **Backend 개발**
  - 결제 도메인 설계 및 구현 (승인·취소·환불·내역 조회)
  - 결제 승인과 예약·티켓 처리 연동

##### 문제 배경

결제를 맡던 팀원이 중도 하차하면서 결제 개발을 넘겨받았습니다. 기존 결제 코드는 결제, 환불, 마일리지, PG사 연동, 결제수단 등 여러 기능이 한 패키지에 섞여 있어 기능 범위가 넓고 도메인 간 책임 경계가 불분명했습니다. 또한 다른 도메인들과 달리 결제 도메인만 헥사고날 아키텍처로 설계되어 있어 프로젝트 전체 구조와 맞지 않았습니다.

이 때문에 기존 로직을 분석하는 데 많은 시간이 들었고, PG사 연동은 실제로 동작하지 않았습니다. 그래서 기존 코드를 고쳐 쓰기보다, 결제 도메인을 핵심 기능 중심으로 처음부터 다시 설계·구현하기로 했습니다.

##### 개선 방법

**결제 엔티티의 독립성 강화.** 결제 엔티티에 금액, 수단, 상태, 결제 완료·취소·환불 시각을 명확히 두었습니다. setter를 두지 않고 승인·취소·환불 메서드로만 상태가 바뀌도록 캡슐화해, 잘못된 상태 전이가 코드 곳곳에서 일어나지 않게 했습니다.

**결제 수단별 공통 흐름.** PG사 연동 대신 실제 예매 흐름과 이어지는 결제 처리에 집중했습니다. 카드 결제와 계좌이체를 각각 지원하되, 두 요청이 같은 추상 요청을 상속해 내부에서는 하나의 결제 처리 흐름을 타도록 했습니다.

**결제 요청 검증.** 결제 요청마다 다음을 확인했습니다.

- 예약 소유자가 요청한 회원인지
- 예약이 결제 가능한 상태인지
- 요청 금액이 예약 운임과 같은지 (금액 위변조)
- 같은 예약에 이미 완료된 결제가 있는지 (중복 결제)

**예약·티켓과의 정합성.** 결제와 예매 데이터가 어긋나지 않도록 하나의 트랜잭션으로 묶었습니다.

- 승인: 결제 승인 → 예약 승인 → 티켓 발급
- 취소: 결제 취소 → 예약 취소 → 좌석 예약·티켓 삭제 → 환불

이 과정에서 예약을 만들 때 바로 발급되던 티켓을 결제 승인 시점에 발급하도록 옮겨, 결제하지 않은 예약에는 티켓이 생기지 않게 했습니다. 환불은 취소된 결제에만 가능하도록 상태 조건도 정리했습니다.

**조회와 식별자.** 결제 내역은 QueryDSL 프로젝션으로 화면에 필요한 컬럼만 조회했습니다. 결제 키는 Redis의 날짜별 증가 카운터로 `날짜-회원번호-일련번호` 형식을 만들고, 카운터는 자정에 만료되게 했습니다.

##### 결과

책임이 결제 하나로 좁혀지면서 결제 도메인의 유지보수성이 크게 좋아졌습니다. 결제 서비스 통합 테스트 9개(성공 4건: 카드·계좌이체 결제, 취소 후 환불, 내역 조회 / 실패 5건: 금액 불일치, 타인 예약 결제, 중복 결제, 타인 결제 취소, 존재하지 않는 회원)로 결제 흐름과 검증 규칙을 고정했습니다.
