#### 역할

- **Backend 개발**
  - OAuth2(Google·Naver·Kakao) + JWT 기반 인증·인가 기능 개발
  - 회원 도메인 개발
  - 회고 통계 기능 개발 (이달 회고 수, 전체 회고 수, 분석 완료 수, 연속 회고일)
  - 전역 예외 처리·공통 응답 형식 등 프로젝트 공통 기반 구성
- **인프라**
  - Prometheus·Grafana 모니터링 시스템 구축
  - LLM 분석 작업 상태를 추적하는 커스텀 지표 개발

| 구분 | 기술 |

| DB | PostgreSQL, Redis |

- 웹 푸시 알림
- OAuth2 소셜 로그인
- 실시간 모니터링
- AWS 배포

<Case no="①" title="Redis를 이용한 멀티디바이스 로그인 처리">

##### 문제 배경

인증·인가 기능을 처음 개발할 때는 한 사용자가 두 대 이상의 기기로 로그인하는 경우를 고려하지 않았습니다. 이 문제를 검증하려고 테스트해 보니, 기기 #1에서 로그인한 뒤 기기 #2에서 로그인하면 기기 #1의 로그인 상태가 덮어씌워졌습니다.

##### 개선 방법

먼저 기기를 구분할 식별자가 필요했습니다. 브라우저에서는 `crypto.randomUUID()`로 기기 고유의 식별자를 만들 수 있으므로, 프론트엔드와 협의해 로그인 요청에 이 식별자를 담도록 했습니다.

다음은 리프레시 토큰을 어디에 저장할지였습니다. 로그인·로그아웃·토큰 재발급은 사용자가 기다리는 동작이라 빨라야 하고, 리프레시 토큰은 정해진 시간이 지나면 버려야 하는 데이터입니다. 그래서 RDB보다 빠르고 키마다 만료 시간(TTL)을 걸 수 있는 Redis를 택했습니다.

저장 구조는 다음과 같이 정했습니다.

- Key는 `refreshToken:{회원 ID}:{기기 ID}`로 만들어 기기마다 토큰을 따로 저장했습니다.
- Value에는 토큰 원문 대신 SHA-256 해시를 저장해, 저장소가 노출되더라도 토큰을 그대로 쓸 수 없게 했습니다.
- 리프레시 토큰의 유효기간을 Redis 키의 TTL로 걸어, 만료된 토큰이 저장소에 남지 않게 했습니다.

##### 결과

토큰 재발급과 로그아웃 때 해당 기기의 키만 검증하고 삭제하게 되어, 한 기기의 동작이 다른 기기의 로그인 상태에 영향을 주지 않게 되었습니다.

</Case>

<Case no="②" title="LLM 분석 작업 모니터링">

##### 문제 배경

회고 분석은 LLM 응답을 기다려야 하는 작업이라 요청부터 결과까지 시간이 걸리고, 실패할 수도 있습니다. 하지만 지금 몇 건이 처리 중인지, 얼마나 성공하고 실패하는지 팀이 한눈에 확인할 방법이 없었습니다.

##### 개선 방법

Micrometer로 분석 작업 전용 지표를 만들고, 분석 시작·성공·실패 지점에서 값을 갱신하도록 연결했습니다.

- **처리 중 건수:** 메모리 카운터로 관리하되, 서버 기동 시 DB의 처리 중 건수로 초기화하고 DB 값과 어긋나면 DB 기준으로 보정했습니다.
- **상태별 누적 건수:** 성공·실패·대기 건수를 DB에서 집계했습니다. 이 지표는 수집할 때마다 DB를 조회하므로, Prometheus 수집 주기를 5초에서 30초로 늘려 DB 부하를 줄였습니다.

Grafana 대시보드에는 기본 JVM·HTTP 지표 옆에 "회고 분석 통계" 섹션을 두어, 처리 중 건수, 상태별 건수, 완료율, 시간당 완료 수를 볼 수 있게 했습니다.

지표가 맞게 움직이는지는 개발 환경에서만 열리는 테스트 API로 시작·완료·실패를 재현해 확인했습니다. 또 코드 리뷰(CodeRabbit)에서 분석이 실패해도 처리 중 건수가 줄지 않는다는 지적을 받아 고쳤습니다. 상태를 실패로 바꾼 뒤에 이전 상태를 확인하던 순서 문제였습니다.

실행 방법, 지표 설명, 조회 쿼리 예시, 트러블슈팅은 `MONITORING.md`로 정리해 팀이 바로 쓸 수 있게 했습니다.

##### 결과

팀이 대시보드에서 분석 작업의 진행·성공·실패 현황을 실시간으로 확인할 수 있게 되었습니다.

</Case>
